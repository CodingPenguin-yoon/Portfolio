# 채용 포트폴리오 콘텐츠 아키텍처

## 1. 목적

이 문서는 기존의 어두운 16:9 발표형 포트폴리오를 대체하는 채용용 포트폴리오의 원고 기준이다.

- 형식은 흰색 바탕의 정석적인 채용 문서로 구성한다.
- 내용은 프로젝트 나열이 아니라 문제 인식, 책임 분리, 실패 대응을 중심으로 구성한다.
- 플랫폼·DevOps 직무를 주축으로 두고 백엔드 구현 역량을 보조 축으로 보여준다.
- 본편은 13페이지를 기본안으로 삼되, 검증 가능한 근거가 추가될 때만 14페이지 이상으로 확장한다.
- 한 페이지에는 하나의 주장만 배치한다.

## 2. 채용 포지셔닝

### 목표 직무

`Platform Engineer / DevOps / Infrastructure Automation`

### 한 줄 정의

> 반복되는 인프라 운영과 배포 문제를 자동화하고, 책임 경계와 실패 복구 구조를 설계하는 신입 플랫폼 엔지니어

### 포트폴리오 전체를 관통하는 메시지

> 반복 작업을 자동화하는 것에서 시작해, 시스템의 책임 경계와 실패 복구 구조까지 설계했습니다.

### 채용 담당자가 읽고 남겨야 할 인상

1. 홈랩을 단순한 장비 취미가 아니라 실제 운영 문제를 발견하고 검증하는 환경으로 사용했다.
2. 최초 설계의 범위가 커졌을 때 기능을 계속 추가하지 않고 책임을 다시 나눴다.
3. 정상 배포만이 아니라 실패 시 기존 서비스와 사용자 데이터를 어떻게 보존할지 고려했다.
4. 구현된 범위와 앞으로의 설계를 구분해 설명할 줄 안다.

## 3. 편집 원칙

### 유지할 정석

- 표지에서 이름, 지원 직무, 핵심 문장을 바로 확인할 수 있어야 한다.
- 초반 두 페이지 안에 지원자의 역량과 대표 프로젝트가 보여야 한다.
- 각 프로젝트는 `문제 → 역할 → 판단 → 구조 → 결과` 순서로 읽혀야 한다.
- 팀 프로젝트에서는 팀 성과와 개인 기여를 분리한다.
- 기술명은 판단과 구현을 설명할 때만 사용한다.

### 특별하게 보여줄 내용

- K-Le-PaaS 경험이 홈랩 자동화 문제로 이어진 과정
- Terraform·Ansible을 포함했던 초기 Heimdall이 비대해진 이유
- VM 수명주기와 애플리케이션 배포를 Gjallar와 Heimdall로 분리한 판단
- 세대 단위 배포와 승격 전 실패 격리
- 애플리케이션 실행 환경과 사용자 데이터의 수명주기를 분리한 판단
- 외부 공개 경로를 Edge와 내부 중계로 나눈 계획

### 금지할 표현

- 답을 강요하는 수사적 질문
- 검증 근거가 없는 `완벽한`, `혁신적인`, `안전한` 등의 형용사
- 기능 목록만 이어지는 설명
- 현재 구현과 계획을 한 문장 안에서 섞는 표현
- 홈랩을 과장된 서비스 규모처럼 보이게 하는 표현
- 실패 후 즉시 롤백이 구현된 것처럼 보이는 표현

## 4. 상태 표기

모든 주요 구조와 기능은 아래 네 상태 중 하나로 표시한다.

- `Implemented`: 코드 또는 실행 증거로 확인된 현재 기능
- `Designed`: 상세 동작과 실패 조건까지 설계됐지만 구현 증거 확인이 필요한 기능
- `Planned`: 방향과 경계만 정한 향후 구조
- `Previous`: 이전에 사용했거나 폐기한 설계

`Designed`와 `Planned`를 `Implemented`처럼 표현하지 않는다. 최종 PDF 작성 전에 저장소, 화면, 로그 또는 실행 결과로 상태를 다시 검증한다.

## 5. 본편 13페이지 구성

### 01. Cover — 어떤 엔지니어인가

**주장**

반복되는 운영 작업을 자동화하고, 서비스의 책임 경계와 실패 복구 구조를 설계한다.

**구성**

- 조윤호 / Platform Engineer
- 한 줄 포지셔닝
- 이메일, GitHub, 웹 포트폴리오, 이력서 링크
- 장식용 슬로건이나 프로젝트 이미지는 사용하지 않는다.

### 02. Profile — 무엇을 해왔는가

**주장**

서로 다른 프로젝트가 플랫폼 운영이라는 하나의 문제 영역으로 연결된다.

**구성**

- 핵심 역량: 배포 자동화 / VM 운영 자동화 / 상태와 실패 추적
- 대표 프로젝트: Heimdall / Gjallar / K-Le-PaaS
- 보조 프로젝트: Argus
- 핵심 기술은 3~4개 범주로만 압축한다.

### 03. Origin — 어떤 불편에서 시작했는가

**주장**

새 프로그램을 올릴 때마다 반복되던 VM, IP, 네트워크, Docker, 배포 설정이 자동화의 출발점이었다.

**구성**

- 기존 수동 흐름: VM 생성 → IP·네트워크 설정 → Docker 설치 → 애플리케이션 배포
- 반복 과정에서 발생한 피로와 설정 편차
- 홈랩을 실제 운영 문제의 검증 환경으로 사용한 배경
- 감정 표현 대신 반복 단계와 운영 비용을 시각화한다.

### 04. Evolution — 설계가 어떻게 바뀌었는가

**주장**

한 번에 모든 것을 자동화하려던 구조에서, 책임을 나눈 두 시스템으로 발전했다.

**구성**

1. K-Le-PaaS를 개발하며 배포 파이프라인과 실행 피드백의 가능성을 경험
2. 초기 Heimdall에 Terraform 기반 VM 생성, Ansible 설정, 애플리케이션 배포를 통합
3. 범위와 의존성이 커지면서 VM 관리와 배포의 변경 이유가 다르다는 점을 확인
4. Gjallar는 VM 수명주기, Heimdall은 애플리케이션 배포로 책임 분리

이 페이지는 포트폴리오 전체의 유일한 연대기 페이지다.

### 05. K-Le-PaaS — 자동화 관점의 출발점

**주장**

자연어 요청을 실제 Kubernetes 작업과 실행 결과로 연결하는 과정에서 자동화의 입력·실행·피드백 구조를 경험했다.

**구성**

- 팀 프로젝트의 목표와 사용 환경
- 전체 흐름: 자연어 요청 → 의도·대상 해석 → API → Kubernetes 작업 → 실행 결과
- 본인이 직접 맡은 API, Kubernetes, 명령 처리 범위
- Heimdall과 Gjallar 설계로 이어진 구체적인 학습

**필수 검증**

- 개인 기여 범위
- 팀 규모와 기간
- 직접 해결한 장애 또는 설계 판단 한 가지

### 06. Current System — 현재 시스템의 책임 지도

**주장**

VM 수명주기, 애플리케이션 배포, 실행 환경, 사용자 데이터를 서로 다른 책임으로 다룬다.

**구성**

- Proxmox 위의 VM 계층
- Gjallar: VM 생성과 설정 자동화
- Heimdall: 애플리케이션 빌드와 배포
- Runtime VM: Docker 기반 실행 환경
- Storage VM: PostgreSQL과 사용자 데이터
- 현재 연결 여부와 운영 상태를 실선·점선으로 구분

### 07. Responsibility Split — 왜 두 시스템으로 나눴는가

**주장**

VM 생성과 애플리케이션 배포는 변경 주기와 실패 영향이 달라 같은 시스템이 소유하지 않도록 분리했다.

**구성**

| 구분      | Gjallar                 | Heimdall                 |
| --------- | ----------------------- | ------------------------ |
| 책임      | VM 수명주기와 기본 설정 | 애플리케이션 빌드와 배포 |
| 주요 대상 | Proxmox VM              | Docker 실행 세대         |
| 변경 이유 | 인프라 용량·구성 변경   | 애플리케이션 릴리스      |
| 실패 영향 | 실행 기반 생성 실패     | 후보 배포 실패           |

- 초기 구조와 분리 후 구조를 작은 Before / After로 비교한다.
- 단순히 프로젝트가 두 개가 됐다는 설명보다 실패 경계가 달라졌다는 판단을 강조한다.

### 08. Gjallar — 반복 가능한 VM 생성

**주장**

Proxmox 기본 템플릿을 상위 템플릿으로 한 번 더 추상화해 VM별 반복 설정을 줄였다.

**구성**

- Proxmox API 기반 실행으로 전환한 이유
- Terraform·Ansible 의존성을 제거한 배경
- 상위 템플릿이 자동화하는 설정 범위
- 요청 → 검증 → 생성 → 설정 → 상태 확인 흐름
- 실제 화면, API 응답 또는 생성 기록 중 하나를 근거로 사용

**필수 검증**

- 현재 자동화되는 정확한 설정 항목
- 승인·감사·마이그레이션 기능의 실제 구현 여부
- 실패 시 재실행 또는 정리 방식

### 09. Heimdall — 검증된 세대만 Current로 승격

**주장**

저장소의 특정 commit을 후보 세대로 격리해 실행하고, health check와 실제 라우팅 검증을 통과한 경우에만 current로 승격한다.

**상태**

`Implemented`

**구성**

- 정확한 commit checkout과 image build
- 단일·다중 서비스의 generation network와 고유 service alias
- candidate container 실행과 service health check
- 프로젝트 Gateway Nginx의 설정 검증, atomic replace, reload
- 실제 route probe 성공 후 current metadata 전환
- 성공 확정 뒤에만 이전 generation 정리
- 프로젝트별 PostgreSQL DB·login role 생성과 deploy-time `DATABASE_URL` 주입

`이전 이미지로 즉시 되돌리기`와 `사용자 데이터 rollback`은 구현 범위가 아니다. 세대 승격과 활성화 실패 복구를 릴리스 이미지 rollback으로 넓혀 표현하지 않는다.

### 10. Heimdall — 실패할수록 보존 범위를 좁힌다

**주장**

실패한 후보가 운영 트래픽과 사용자 데이터에 영향을 주지 않도록 실행 세대, 라우팅 설정, 데이터 수명주기를 분리했다.

**상태**

`Implemented` — 단, 이미지·데이터 rollback과 DB backup·restore는 비범위

**구성**

- Current와 Candidate의 동시 실행 및 generation별 네트워크 격리
- 승격 전 실패: Candidate 미승격, 기존 Current와 active metadata 유지
- Nginx last-known-good 설정 복원과 실패한 세대의 exact-label 정리
- Worker 재시작 시 Control DB, Nginx 응답 marker, Docker label을 비교하는 reconciliation
- 상태를 확정할 수 없으면 자동 삭제보다 후보 보존을 선택
- 배포 진단 로그 보존과 프로젝트 DB·사용자 secret 마스킹
- 프로젝트별 PostgreSQL DB와 login role provisioning
- 별도 Storage VM의 PostgreSQL을 배포 세대와 독립적으로 유지하는 운영 구조
- 실패 범위 표: source deployment / route activation / worker interruption / user data

**정확성 규칙**

- 세대 병행, Nginx 승격, last-known-good 복원, reconciliation은 현재 코드로 확인된 구현이다.
- 프로젝트별 DB·role 생성과 배포 연동은 구현됐지만 삭제·purge·rotation·backup·restore는 구현 범위가 아니다.
- 성공한 과거 배포를 source에서 다시 빌드할 수는 있지만 저장된 image를 즉시 승격하는 release rollback은 아니다.
- 별도 Storage VM은 사용자가 확인한 실제 운영 구조이며, 로컬 기본 Compose의 물리적 장애 격리 기능으로 표현하지 않는다.

### 11. External Exposure — 외부 공개 구조

**주장**

외부 Edge는 고정하고, 배포에 따라 바뀌는 라우팅은 내부에서 처리하도록 경계를 나눴다.

**상태**

`Planned`

**구성**

- DNS 분리: 사용자용 Control Web / 사용자 배포용 wildcard domain
- OCI Edge Nginx: 공인 TLS 종료와 Host 전달
- WireGuard tunnel
- 홈랩의 분리된 외부망과 Internal Ingress Nginx
- Project Gateway의 서비스 선택과 세대 승격
- Runtime application과 별도 PostgreSQL Storage VM

OCI 설정을 배포마다 변경하는 구조처럼 표현하지 않는다. 도메인별 동적 중계는 내부 Ingress가 담당한다.

### 12. Argus — 다른 문제에 적용한 같은 원칙

**주장**

여러 데이터 공급자의 입력을 독립적으로 수집하고 정규화해 하나의 비교 가능한 흐름으로 만들었다.

**구성**

- 수집기 분리
- 데이터 형식 정규화
- 백엔드 계산과 대시보드 연결
- 플랫폼 포트폴리오의 주 서사를 방해하지 않도록 한 페이지 이하로 제한

### 13. Resume & Contact — 판단을 요약하고 끝낸다

**주장**

운영 문제를 발견하고, 자동화하고, 책임과 실패 경계를 다시 설계할 수 있다.

**구성**

- 프로젝트별 한 줄 요약과 상태
- 핵심 기술 범주
- 교육과 자격
- GitHub, 이메일, 이력서 링크
- `감사합니다`만 있는 별도 종료 페이지는 만들지 않는다.

## 6. 시각 자료 계획

본문에는 다음 다섯 개의 다이어그램만 우선 제작한다.

1. 수동 홈랩 설정 흐름
2. K-Le-PaaS → 초기 Heimdall → Gjallar·Heimdall 분리 과정
3. 현재 책임 지도
4. Heimdall Candidate → 검증 → Promotion → 실패 복구 흐름
5. DNS → OCI Edge → WireGuard → Internal Ingress → Runtime / Storage 계획

다이어그램은 기술 로고 모음이 아니라 책임과 데이터 흐름을 보여줘야 한다. 스크린샷은 구현 근거를 증명할 때만 사용한다.

## 7. 디자인 방향

- A4 세로 또는 A4에 가까운 세로형 화면 비율
- 흰색 배경, 검정 본문, 회색 보조 정보
- 프로젝트별 강한 색상 브랜딩은 제거하고 상태와 구분에만 제한적으로 사용
- 카드 남용 없이 제목, 본문, 표, 다이어그램의 문서 위계로 구성
- 본문 최소 글자 크기와 여백을 먼저 고정하고 페이지 수를 조정
- 페이지 번호와 프로젝트·상태 라벨을 일관되게 배치
- 한 페이지를 훑는 순서가 `제목 → 주장 → 근거 → 결과`로 고정되도록 한다.

## 8. 구현 전 검증 목록

다음 항목이 확인되기 전에는 최종 문구로 확정하지 않는다.

- K-Le-PaaS에서 본인이 직접 소유한 코드와 설계 범위
- Gjallar의 현재 구현 기능과 템플릿 자동화 항목
- Heimdall의 generation 승격·활성화 실패 복구·재시작 reconciliation 범위
- Heimdall과 Gjallar의 현재 연동 여부
- PostgreSQL 분리 VM과 프로젝트별 DB·user 구성의 현재 상태
- 외부 공개 구조가 계획 단계라는 표기
- 실제 화면, 로그, API, 코드 중 각 주요 주장에 연결할 근거
- 이력서의 `이미지 롤백`, `관리형 PostgreSQL 자동 생성` 문구와 실제 구현 범위의 일치 여부
